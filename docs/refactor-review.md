# qmwx-image 重复处理审查与精简记录

审查基于修改前提交 `4d01b78` 与当前工作区实际调用链。先完成审查，再实施局部修改。未新增识别、测量或三维重建算法，未更改 API 路径、响应字段、档案模型或依赖。

## 1. 原有问题与判断

| 位置和实际调用 | 原因与是否合并 | 合并风险及处理 |
| --- | --- | --- |
| `ImageCollectionService.collect()` 调用 `inspect_image()`，随后 `Pipeline.run()` → `ImageMetadataProcessor.process()` 再调用同一函数 | 默认流程每张图片完整验证两次。每次都先打开并 `verify()`，再打开并 `load()`；可复用本次真实验证结果 | 不能把 `ImageAsset` 或外部字典视为验证证据。新增只能由真实文件检查生成的调用内凭据；文件或限制变化时重新完整检查 |
| `routes.create_object()` 与 `collect()` 都对名称去空格、检查长度和控制字符，都检查图片非空和数量 | 名称规则完全相同；业务服务必须独立验证，可集中到服务。路由中的空列表和重复数量判断可去掉 | HTTP 表单结构、字段类型和解析器数量上限仍保护请求解析，不能一并删除 |
| `collect()` 自己创建 `.upload`、写入、计算 SHA256、按真实格式改名；`ObjectTransaction` 另负责 JSON 与目录提交 | 文件持久化职责分散。写入与命名可以移入既有事务类 | 保留原有流式大小限制、源流所有权、格式扩展名白名单和整批回滚；新增加目标文件不覆盖检查 |
| `Pipeline.run()` 已复制整个档案，又复制其中的图片和历史结果 | 都属于同一个处理模块的隔离快照，后两次复制没有额外隔离收益 | 每模块保留一个完整深拷贝；测试确认模块修改快照不会影响原档案或后续模块 |
| `ObjectTransaction.committed` 仅赋值，没有读取 | 没有控制提交或清理行为，可以删除 | 提交仍由 `os.replace()` 完成；退出时清理剩余暂存目录 |
| `stage_image()` 原循环的 `while chunk := stream.read(...)` | 延续旧循环时发现 `None`、空字符串或空 bytearray 会被误当 EOF；完整图片后接这种返回值也会被接受 | 改为先检查 `bytes`，只有空 bytes 才是合法 EOF；直接调用服务的回归测试覆盖 |

`inspect_image()` 内部的 `verify()` 和重新打开后的 `load()` 承担不同检查：一个检查文件结构，一个真正解码像素。此次没有合并这两个步骤，也没有只读文件头就接受图片。

## 2. 磁盘写入核实

按当前依赖的默认 multipart 配置，单文件超过 1 MiB 后，解析器会把上传流写到 `.multipart`；较小文件保留在内存。业务事务再把输入流写入 `.staging`，同时计算校验值。因此，小图通常写一次图片内容，大图确实写两次。

`LocalMultipartParser.on_headers_finished()` 替换的是 Starlette 刚创建的空内存 spool，原 spool 尚无图片内容，不是第三次落盘。`.upload` 改为 `.png/.jpg/.webp` 和最终目录提交都是同一数据目录内的移动，也不是再次写入整张图片。JSON 的临时写入与替换只针对档案。

这次保留 HTTP spool：它限制解析时的内存占用，处理截断请求并关闭未完成的文件。业务暂存目录另保证多图、处理结果与 JSON 整批发布。Windows 的 `SpooledTemporaryFile` 带有关闭删除行为，直接移动其底层文件需要改变解析器和业务层之间的所有权，还可能依赖私有属性；这超出了低风险精简范围。

没有正式发布前，数据都位于 `.staging`。先完整保存并校验 JSON，再用 `os.replace()` 发布整个物体目录；图片写入、改名、JSON 保存或提交失败时，事务退出会清理暂存数据，HTTP 层最终关闭解析文件。模块自身失败被记录为标准结果，仍可发布带警告的有效基础档案，与输入损坏或存储失败导致的回滚区分开。

## 4. 修改前后流程

修改前：

```text
HTTP 解析 → 路由业务校验 → 服务重复业务校验
  → 服务写暂存图片并计算 SHA256 → 完整验证① → 服务改名
  → Pipeline → 元数据模块完整验证② → Assembler → JSON → 提交目录
```

修改后：

```text
HTTP 解析及请求结构检查 → 服务统一业务校验
  → 存储限量写暂存图片并计算 SHA256 → 完整验证一次并生成凭据
  → 存储改名 → Pipeline → 元数据模块确认文件未变并复用元数据
  → Assembler → JSON → 提交目录
```

每张图默认完整验证次数由 2 次变成 1 次，显式 `Image.open()` 从 4 次变成 2 次，显式像素 `load()` 从 2 次变成 1 次。此处是调用次数比较，没有进行耗时基准测试，不代表端到端上传速度翻倍。

凭据仅在本次 Python 调用中存在：构造时必须实际完整检查；保存不可变的元数据和文件身份、大小、修改时间；只允许同目录同名主干的扩展名改名。模块会先执行原有路径检查，再确认凭据类型和文件状态。外部字典不被信任，元数据副本不能修改凭据。无凭据、文件被改动/替换/移走，或像素上限变严时，回到原完整验证流程。它不是持久缓存，也不是针对恶意本机进程篡改的安全边界。

## 6. 保留事项及后续建议

- 保留 `routes → collection → pipeline → modules → assembler → storage/models` 的职责划分；没有删模块或将未来算法塞入采集服务。
- 大图的两次图片内容写入暂未消除。若将来实测磁盘 IO 成为瓶颈，应单独设计命名临时文件与事务交接，在 Windows 上验证关闭删除、取消上传、跨设备移动和失败恢复。
- 保留 HTTP 请求限制与业务服务限制、完整验证内部两步骤，以及模型/合并/持久化的边界校验；它们承担不同职责。
- 正常异常退出时有回滚；进程被强制终止或机器断电后的陈旧暂存目录回收仍未实现。它们不位于正式 `objects` 中，本次没有扩大为恢复系统。
- 未实现的识别、尺度估计、三维重建等功能仍保持未实现状态。未修改网页流程，也未代替手机局域网实机验收。

这些变更减少了已确认的重复计算，并集中实际文件持久化操作。进一步削减文件数或引入通用缓存、事务框架没有足够收益，因此未做大规模重构。
