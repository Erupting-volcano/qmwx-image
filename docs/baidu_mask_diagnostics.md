# 百度返回 Mask 的诊断与一次性真实验收

本文对应 2026-11-08 的百度智能抠图排查。本轮只做源码检查、本地构造图像和模拟 HTTP 测试，**没有执行真实百度分割请求**。真实验收必须等开发者明确确认后单独进行；上传新照片、重新建立档案或重复运行烟测都可能再次消耗额度。

本轮全量回归结果：原有测试 **599 项通过**，新增诊断测试 **25 项通过**，合计 **624 passed、0 failed、1 skipped**。跳过的是现存真实付费 API 烟测，另有一项既有 Starlette TestClient/httpx 弃用警告。P/RGB/RGBA 测试验证当前明确拒绝和诊断，不代表已实现这些编码的兼容，也不代表真实返回已验收。

## 已知证据和当前结论

已在本机失败档案中找到与开发者提供的错误编号完全一致的记录。该记录只有以下泛化错误，没有保存原始返回图片、返回模式或返回尺寸：

```text
API掩码的格式、模式或尺寸与送入API的图片不一致。
```

从原有 `_decode_mask()` 的执行顺序可以确认：该次处理已经取得非空 `image` 字段，完成严格 Base64 解码和解码后字节数限制检查，并由 Pillow 识别了图像头；随后在格式、模式、尺寸或帧数的组合检查中被拒绝。**这不证明返回图片已经完整解码，也不能确定具体是哪项检查失败**，因为原来的 `returned.load()` 位于该组合检查之后。

本地保存的原图为 JPEG，编码尺寸 `3072 × 4096`，EXIF 方向为 `1`。根据当前代码复现得到的尺寸链如下；其中 API 输入尺寸是按当前实现推算，并非从那次历史网络请求中捕获的值：

| 环节 | 尺寸或状态 | 证据性质 |
| --- | --- | --- |
| 本地原图 | `3072 × 4096`，EXIF 方向 `1` | 本机图片头与档案记录 |
| EXIF 转正后 RGB | `3072 × 4096` | 方向 `1` 不交换宽高 |
| 等比缩小后的 API 副本 | `2250 × 3000` | 当前 `_prepare_image()` 的本地复现 |
| 补边 | 不需要 | 缩小后两边均不小于 `128` |
| 百度实际返回 | 格式、模式、尺寸、透明信息均未知 | 未保留原始返回图片或诊断字段 |
| 去边后的掩码 | 若响应通过尺寸检查，应为 `2250 × 3000` | 条件说明，不代表历史响应已通过 |
| 最终原图坐标掩码 | 若处理成功，应为 `3072 × 4096` | 最近邻回映射的目标尺寸 |

本地构造数据能复现：同尺寸的调色板 PNG、RGB PNG、RGBA PNG，以及错误尺寸的 L PNG，原来都会触发同一句错误。这个复现证明原错误缺少定位信息，**不能证明真实百度响应采用了其中某一种编码**。

因此本轮保留现有格式接受范围，不在缺少真实返回样本时增加 `P/RGB/RGBA` 转灰度或透明度猜测。格式兼容问题仍需根据真实返回的像素、调色板及透明通道语义决定，不能把“Pillow 能打开图片”当作“图片一定是正确 Mask”。

另外，本地重现了一个独立的透明信息风险：`L/1` PNG 也可以携带 `tRNS` 透明信息，仅检查模式后调用 `convert("L")` 可能忽略它。现在明确拒绝这种尚未确认语义的输入。这是本地证实的安全边界问题，**不能据此断言它是上述历史失败的原因**。

## 服务端诊断应如何使用

新的 `baidu_mask_decode` 日志只记录有界的格式、尺寸和处理状态，不记录图片内容。重点查看：

| 字段 | 用途 |
| --- | --- |
| `response_format` | Pillow 识别的真实文件格式 |
| `response_mode` | Pillow 识别的模式，例如 L、1、P、RGB、RGBA |
| `response_width/response_height` | API 返回图片的实际宽高 |
| `expected_width/expected_height` | 本次送入 API 的副本宽高 |
| `decoded_byte_length` | 严格 Base64 解码后实际字节数 |
| `frame_count/has_transparency` | 帧数及是否携带透明信息 |
| `decode_status` | 区分缺字段、Base64、图像头、完整解码及安全检查的失败环节 |
| `normalization_status` | 区分未执行归一化、模式拒绝及成功归一化等状态 |

`decode_status` 包括 `invalid_image_field`、`invalid_base64`、`decoded_size_rejected`、`header_read`、`pixels_loaded`、`image_decode_failed` 等阶段。`normalization_status` 用 `rejected_format/rejected_animation/rejected_dimensions/rejected_mode/rejected_transparency` 区分拒绝原因；`binary_l` 和 `thresholded_128` 表示实际完成的归一化方式。它们只是文件处理状态，不是分割质量结论。

`baidu_mask_geometry` 日志使用同一个 `diagnostic_id`，记录 `original_width/height`、`api_width/height`、`unpadded_width/height`，以及成功回映射后才有值的 `final_width/height`。其中 `original` 指传入 Backend 的 EXIF 转正 RGB 尺寸。尺寸不匹配必须在去边或回映射之前拒绝，不能用拉伸掩盖错误。

诊断字段只在服务端日志中出现。页面和 `ObjectProfile` 只保留必要的中文错误说明和既有错误编号，不复制完整日志对象或原始百度响应。日志不得包含 API Key、Secret Key、Access Token、完整敏感请求地址、Base64、像素矩阵或异常中夹带的响应正文。

查看某个失败时，应保留对应时间及上层错误编号。原有分割处理器的异常日志会附带“百度掩码服务端诊断编号”，用它关联 `baidu_mask_decode` 和 `baidu_mask_geometry` 的 `diagnostic_id`。诊断编号与档案错误编号不是同一个值；异常附注不会进入页面使用的 `str(error)`。并发请求的日志可能交错，不能只凭相邻位置把另一张图片的尺寸当成本图响应。

## 当前格式边界

- 只接受符合安全大小、实际 API 输入尺寸及单帧要求的 PNG。
- `L/1` 模式沿用现有处理规范，最终输出为 `L` 模式的 `0/255` 二值图。原有灰度边缘阈值处理会明确给出提醒。
- 即使是 `L/1`，携带 `tRNS` 透明信息时也明确拒绝；归一化成功的输出不继承响应 PNG 的 EXIF、透明或其他附加元信息，以免保存或预览时再次改变解释。
- 调色板、RGB、RGBA 和其他尚未确认语义的模式继续拒绝，并通过服务端诊断说明具体模式。
- 透明信息不能直接忽略，也不能仅凭存在 Alpha 就将它当作前景。若透明通道语义未被确认，应停止处理。
- 空前景保持 `not_found`，不保存假掩码；全白结果需要人工复查，不能声称目标已正确分割。
- 不下载响应中的任意 URL，不把矩形框填充成掩码，不在失败时生成模拟成功结果。

普通照片也可以使用某些灰度编码。格式和尺寸检查是必要的文件安全边界，不能单独证明分割语义与物体轮廓正确；真实样例仍需人工检查。

官方接口说明区分 `return_form=mask` 与 `return_form=rgba`：前者是原图大小的前景/背景掩码，后者是保留主体的透明背景图。只有取得真实返回并确认它属于哪种语义，才可以决定是否需要兼容新的 PNG 编码。依据：[百度智能抠图接口文档](https://cloud.baidu.com/doc/IMAGEPROCESS/s/rm8zl3koj)。

## 真实验收前的准备：本次不执行

1. 开发者明确确认“一张指定日常物品照片、一次百度分割请求”，同时确认照片可以发送给百度。没有此确认，不进行付费验收。
2. 选择一张照片及一个目标框，保存原图校验值、原始尺寸、EXIF 方向、转正后尺寸和比例框。原图保持不变，避免拍摄信息或框选变化影响对比。
3. 使用百度后端的独立验收调用，不运行整条默认采集流水线，不触发物体理解或其他外部模型。使用当前 `method=control`、`return_form=mask`、`refine_mask=false` 请求约定，不更换接口或模型。
4. 在被 Git 忽略的 `data/acceptance/<唯一验收编号>/` 中预留本地证据目录，先确认没有同编号的已尝试记录。记录本次代码提交、确认时间和输入校验值；不保存凭证、完整请求 URL 或请求体。
5. 准备一次性调用保护：在分割 POST **之前**，用独占创建方式写入 `segment-attempted` 标记并记录开始时间。标记已存在即停止，不能覆盖后重试。鉴权请求与分割请求分别计数，令牌获取不计为第二次分割请求。
6. 若分割请求超时、进程中断或响应丢失，保留标记并将结果记为 `unknown`，不要自动重试。网络失败不代表百度一定没有收到或计费。

这是一份待确认的验收方案，不是已经运行的验收脚本。本轮未创建验收目录或尝试标记，也没有准备会在启动时自动运行的付费命令。

## 确认后的一次请求与证据保存

执行者在开发者确认之后按以下次序完成，任一失败都停止，不追加分割请求：

```text
检查验收编号和输入未变化
  → 验证/转正原图并准备 API 副本
  → 获取或复用令牌
  → 独占写入一次性尝试标记
  → 只发出一次分割 POST
  → 捕获返回 image 的解码后原始字节
  → 离线检查格式、模式、透明信息和实际尺寸
  → 通过安全检查后归一化、去边、回映射
  → 保存处理后的 Mask 和安全记录
  → 人工检查对齐与分割质量
```

必须在归一化前保留真实返回字节，才能分析原始编码。捕获阶段继续执行 Base64 字符和解码字节数上限；不能为保存证据而接收无限大的响应。有效且大小受限的返回字节先作为私有的 `response-image.bin` 保存，确认文件格式为 PNG 后可记录为 `response-image.png`。此文件名表示“返回图片”，不表示已经证明是正确 Mask。Base64 无法安全解码时不保存原始响应正文，只记录失败阶段及安全长度信息。

若解码、模式或尺寸检查失败，保留这次原始返回图片和安全诊断，停止归一化、业务保存及质量判定。不能把原始图片强制转 L 或伸缩后命名为“成功掩码”。如果通过检查，再分别保存 API 尺寸下的归一化掩码、去边与回映射后的二值掩码，以及必要的安全尺寸记录。

这些文件属于有验收编号可追踪的私有证据，不手工复制进正式 `objects/` 档案目录，也不提交 Git。正式业务产物仍通过现有事务存储接口保存。原始返回照片或掩码也可能包含用户图像信息，不能放入日志、聊天或公开仓库。

## 四项结果必须分别记录

建议验收记录使用以下独立状态；初始化均为 `not_run`，不得预填成功：

| 项目 | 何时才可以标为通过 |
| --- | --- |
| 模拟测试 | 本地构造数据和模拟 HTTP 的自动化测试实际通过；只说明代码分支符合测试预期 |
| 真实 API 调用 | 唯一一次分割请求确实得到成功响应；超时等不明情况记为 unknown |
| 真实掩码处理 | 真实返回通过完整解码、安全检查、归一化与坐标回映射，并保存可追踪文件 |
| 人工分割质量 | 人工对照原图确认目标和边缘质量；需要记录检查人、时间与结论 |

安全记录可包含：验收编号、代码提交、输入校验值、分割尝试次数、以上四项状态、白名单诊断、产物相对路径和人工复查意见。不得包含密钥、令牌、完整 Base64、敏感请求 URL 或整个百度响应。

人工复查至少逐项记录：

- 掩码和 EXIF 转正原图是否对齐，宽高及方向是否正确。
- 目标是否正确，是否错误选中背景或其他物体。
- 物体外边缘、细长部分、孔洞和凹陷是否完整。
- 是否存在明显背景残留、缺失区域或几乎全图覆盖。
- 在原图与回映射掩码的本地叠加预览中，是否出现系统性平移、缩放或旋转偏差。

接口成功、PNG 解码成功、文件保存成功都不能代替这一步。质量不合格时保留失败意见和证据，不把自动化测试结果改写成“真实分割合格”，也不为得到更好效果而自行追加调用。

## 下一步

当前具备准备一次受控真实验收的代码入口和诊断方案，但**没有确认历史失败的实际返回模式、尺寸或透明语义，也没有证明任何真实分割质量合格**。取得开发者明确确认后，按上述一次性捕获方案保留返回证据；如果开发者已有那次返回的 PNG，可先离线重放解码检查，避免消耗新的 API 额度。
